`llmwiki rm` undoes an ingest: it deletes a source file, deletes the concept pages that source exclusively owns, and leaves any page another live source also contributed to untouched. There is no confirmation flag - a bare `rm` applies immediately - so `--dry-run` is the only pre-flight check available.

## Basic usage

```bash
llmwiki rm <source>
```

Run it from your project root, the same as any other llmwiki command.

<Note>
No LLM provider credentials are required. `rm` never calls the chat model, and it does not need a working embeddings backend either - see [Embeddings after a removal](#embeddings-after-a-removal).
</Note>

## Flags

| Flag | Description |
|------|-------------|
| `--dry-run` | Print what would be deleted and kept, without acquiring the project lock or changing anything. Default: off - a bare `rm` applies immediately. |

## What gets deleted

| Item | Result |
|------|--------|
| The file under `sources/` | Deleted |
| Pages under `wiki/concepts/` derived only from that source | Deleted |
| Pages under `wiki/concepts/` another live source also contributed to | Kept, untouched |
| The source's entry in `.llmwiki/state.json` | Removed |
| `wiki/index.md` and `wiki/MOC.md` | Regenerated |
| Vectors for the deleted pages in `.llmwiki/embeddings.json` | Pruned |

<Note>
`rm` only ever acts on the concepts namespace. If your project uses a Configurable Lifecycle Profile with typed entity pages elsewhere in `wiki/`, deleting a source here does not remove or report on those pages.
</Note>

## Naming the source

Pass the filename under `sources/`, with or without the `.md` suffix:

```bash
llmwiki rm research-notes.md
llmwiki rm research-notes
```

To find the exact filename, look in the `sources/` directory of your project.

`rm` matches on filename only. You cannot pass the original URL or local path you ingested. If `<source>` doesn't match a file under `sources/`, `rm` changes nothing and exits `1`.

## Example

```bash
llmwiki rm research-notes.md --dry-run
```

```
x Would delete: sources/research-notes.md
x Would delete: wiki/concepts/deprecated-api.md
i Kept: wiki/concepts/authentication.md (shared with other sources)
```

Drop the flag to apply:

```bash
llmwiki rm research-notes.md
```

```
x Deleted: sources/research-notes.md
x Deleted: wiki/concepts/deprecated-api.md
i Kept: wiki/concepts/authentication.md (shared with other sources)
~ Regenerated index and MOC
```

The embeddings refresh reports its own outcome separately - see [Embeddings after a removal](#embeddings-after-a-removal) - rather than being folded into that summary line, so a failure there can never be masked by a blanket success message.

## What `rm` reports but doesn't fix

Deleting a page can leave a surviving page's `[[wikilink]]` pointing at something that no longer exists, and can leave a pending review candidate referencing a source that's now gone. `rm` reports both without editing anything for you:

- A broken wikilink is reported as the surviving page's path and the doomed target. Run [`llmwiki lint`](/cli/lint-eval) for the full detail.
- A pending candidate that references the removed source is reported by count. Run [`llmwiki review list`](/cli/review) to see it.

## Safety boundaries

A symlinked entry in `sources/` is never treated as a source - `rm` resolves it the same as a missing file. A concept slug that would escape `wiki/concepts/` fails a filename-safety floor: rather than deleting through it, `rm` leaves the page on disk, warns `Not deleted: <slug> (floor:unsafe-slug)`, and exits `1`. This floor is defense in depth; a normally-compiled slug never trips it.

Page deletes apply as one journalled batch. If the process is killed partway through, the next `rm`, the next `compile`, or `llmwiki recover` restores any pages from that batch that had already been removed. The source file itself is deleted first, outside that journal - if the process dies between deleting the source and deleting its pages, the source stays gone and the pages remain on disk, and the next `compile` treats them like any other pages whose owning source disappeared.

`rm` runs under the project lock (`.llmwiki/lock`). If another llmwiki process already holds it, `rm` refuses cleanly and exits `1` rather than waiting or forcing. `--dry-run` never takes the lock at all.

## Embeddings after a removal

The removal itself has no new text to embed, but the refresh that runs after it is the same full refresh every other command uses, not a pruning-only variant. It always prunes the deleted pages' vectors, and it also embeds any other eligible page that doesn't already have a stored vector - so `rm` can call your embeddings provider even for pages it didn't touch.

This step is attempted even when no embeddings backend is configured - it is not skipped. A missing or invalid backend surfaces as a warning instead:

```
! Skipped embeddings update: page embedding failed [auth] at "concepts/shared": VOYAGE_API_KEY is not set. Anthropic embeddings use Voyage - set VOYAGE_API_KEY to enable semantic search.
```

By default, a failed embeddings refresh only prints that warning and `rm` still exits `0`. If you've set [`LLMWIKI_EMBED_STRICT`](/configuration/environment-variables#embeddings), the same failure makes `rm` exit `1` too, matching every other llmwiki command.

<Note>
Either way, the delete has already happened by the time embeddings run: the source file, the deleted pages, and `.llmwiki/state.json` are all written before the embeddings step starts. A non-zero exit here means your embedding index is stale, not that the removal was rolled back or partially applied.
</Note>

## Exit codes

| Outcome | Exit code |
|---------|-----------|
| `<source>` doesn't match a file under `sources/` | `1` |
| `--dry-run` on a match | `0` |
| Applied; no pages were skipped | `0` |
| Applied; one or more pages were skipped (filename-safety floor) | `1` |
| A page fails mid-delete (survives its unlink, or a symlinked/oversized page is refused by the pre-state check) | `1`, uncaught `Error:` - see [safety boundaries](#safety-boundaries) |
| Another llmwiki process holds the project lock | `1` |
| Embeddings refresh failed with `LLMWIKI_EMBED_STRICT` set | `1` |
